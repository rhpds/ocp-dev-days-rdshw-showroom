== Laboratorio 5 - Gobernanza de LLM

Coloque una capa de gobernanza delante del endpoint de LLM mediante Connectivity Link. Aplique autenticación con clave de API y límites de velocidad basados en tokens en varios niveles de servicio.

{empty} +

=== El escenario

En los laboratorios anteriores, creó un agente de IA que resuelve problemas de atención al cliente mediante lenguaje natural. El agente consulta la base de datos, actualiza registros y vuelve a generar documentos de pólizas, todo desde la interfaz de chat.

Ahora quiere ampliarlo con una nueva capacidad: **análisis del perfil del cliente**. Cuando un agente de soporte pregunta por un cliente, la IA analiza sus datos y devuelve un resumen estructurado. Hay dos niveles de análisis disponibles:

* **Oro** -- historial completo de pólizas, historial de reclamaciones y estado de fidelidad.
* **Plata** -- pólizas recientes e información básica del perfil.

El nivel Oro consume más tokens porque el análisis es más profundo y la respuesta más completa. El nivel Plata requiere menos. El sistema está diseñado con una estrategia de respaldo: si se agota el presupuesto de tokens del nivel Oro, el servicio recurre al nivel Plata. Si también se agota el de Plata, la solicitud se aplaza.

Pero antes de que todo esto funcione, necesita gobernanza. ¿Quién puede acceder al endpoint de LLM? ¿Cuántos tokens puede consumir cada nivel? Sin controles, nada impide que un consumo descontrolado agote el presupuesto de API de la organización.

En este laboratorio, colocará una **capa de gobernanza** delante del endpoint de LLM mediante link:https://www.redhat.com/en/technologies/cloud-computing/connectivity-link[*_Red Hat Connectivity Link_*,window=_blank]. Implementará dos políticas:

* **AuthPolicy** -- Controlar _quién_ puede acceder al endpoint mediante autenticación con clave de API y autorización basada en grupos.
* **TokenRateLimitPolicy** -- Controlar _cuánto_ puede consumir cada nivel al aplicar límites de velocidad basados en el uso real de tokens.

{empty} +

=== ¿Por qué Connectivity Link?

Este es exactamente el tipo de problema para el que se diseñó _Red Hat Connectivity Link_. Basado en el proyecto link:https://kuadrant.io/[_Kuadrant_,window=_blank], incorpora gobernanza consciente de la IA a *Kubernetes*:

* **Limitación de velocidad consciente de los tokens** -- los límites se basan en los tokens realmente consumidos, no en el número de solicitudes. Esto es lo que hace viables los servicios de IA por niveles: cada nivel obtiene su propio presupuesto de tokens, aplicado en la puerta de enlace.
* **Sin cambios de código** -- las políticas se aplican en el nivel de infraestructura. El agente de IA y el código de integración no se modifican.
* **Nativo de Kubernetes** -- las políticas son CRD estándar, se aplican con `oc apply`, se almacenan en Git y se revisan en PR. No se necesita una consola de administración independiente ni un plano de control de proveedor.
* **Componible** -- una política extrae la identidad y otra la utiliza para los presupuestos de tokens por nivel. Se superponen de forma declarativa.

Estas capacidades provienen de la forma en que Connectivity Link se basa en el estándar _Kubernetes Gateway API_. Antes de empezar a configurar políticas, veamos el modelo de Gateway API.

{empty} +

=== El modelo de Gateway API

Connectivity Link se basa en _Kubernetes Gateway API_, el estándar para administrar el enrutamiento del tráfico en _Kubernetes_. Comprender este modelo hará que los ejercicios siguientes resulten intuitivos.

Estos son los componentes básicos:

* **GatewayClass + Gateway** -- pertenecen al equipo de la plataforma. Definen _cómo_ entra el tráfico al clúster. Ya están aprovisionados.
* **HTTPRoute** -- pertenece al equipo de la plataforma o de desarrollo. Define _adónde_ se dirige el tráfico (en este caso, a la API de LLM).
