== Habilitar la conectividad con la base de datos

El flujo de integración necesita acceder a la base de datos, pero todavía no puede alcanzarla. Averigüemos por qué y habilitemos la conexión.

NOTE: Este ejercicio utiliza un solo clúster para centrarse en lo esencial, pero Service Interconnect está diseñado para mucho más de lo que puede manejar una política de red: mallas multisite que abarcan clústeres, regiones y proveedores de nube. Al final se incluye un breve ejemplo del mundo real que muestra este contexto más amplio.

{empty} +

=== ¿Por qué no puedes acceder a la base de datos?

La base de datos de backend está alojada en un espacio de nombres aislado (*shared-database*) con políticas de red estrictas: no se permite el acceso directo desde otros espacios de nombres.

=== Conectar espacios de nombres con Service Interconnect

{rhsi} (desarrollado a partir del proyecto de código abierto https://skupper.io[Skupper.io,window=_blank]) resuelve este problema creando conexiones cifradas a nivel de aplicación entre espacios de nombres, sin necesidad de VPN, reglas de firewall ni exponer servicios a la red pública.

Una vez configurado, se crea un servicio local en tu espacio de nombres que reenvía de forma transparente el tráfico a la base de datos remota:

[.mermaid-hints-simple]
****
S2 | Site | La base de la red de Skupper. Cada espacio de nombres participante ejecuta un Site. Los Sites se descubren entre sí mediante AccessGrants y AccessTokens. +
S1 | Site | La base de la red de Skupper. Cada espacio de nombres participante ejecuta un Site. Los Sites se descubren entre sí mediante AccessGrants y AccessTokens. +
Grant | AccessGrant | Se crea en el lado receptor. Genera credenciales que permiten que un Site remoto se conecte. Es como una invitación para unirse a la red. +
Token | AccessToken | Se crea en el lado que inicia la conexión usando los datos del grant. Establece el enlace cifrado entre dos Sites. +
Listener | Listener | Expone localmente un servicio remoto en tu espacio de nombres. Coincide con un Connector del otro lado mediante la clave de enrutamiento, para que el servicio remoto aparezca como local. +
Connector | Connector | Conecta un servicio local a la red de Skupper. Publica el servicio para que los Listeners coincidentes de otros espacios de nombres puedan acceder a él. +
SVC2 | Service (creado automáticamente) | Al crear un Listener, Service Interconnect crea automáticamente un servicio local de Kubernetes. Tu aplicación se conecta a este servicio como si la base de datos fuera local.
****

TIP: Pasa el cursor sobre cada componente del diagrama para saber qué hace.

La base de datos se encuentra en un entorno seguro y aislado: no hay puertos de entrada expuestos. Para mantenerlo así, el enlace se inicia *desde* el lado de la base de datos *hacia afuera*, en dirección a tu Site. Por eso creas un AccessGrant de tu lado: le da permiso al Site de la base de datos para conectarse contigo y establecer un enlace de comunicación bidireccional. Su entorno nunca abre un punto de entrada que pudiera ser objeto de un ataque.

{empty} +

=== Lo que harás

Toda configuración de Service Interconnect consta de dos etapas: primero *estableces la red*, la malla segura que conecta tus entornos, y luego *expones servicios* a través de ella. Una vez establecida la red, para agregar un servicio nuevo solo tienes que emparejar un Listener con un Connector; no es necesario modificar la red.

=== Establecer la red

El primer paso es configurar la red segura entre tu espacio de nombres y el de la base de datos. Para ello, debes crear un Site, un AccessGrant y un AccessToken; juntos, establecerán un enlace cifrado entre ambos entornos.

==== Paso 3: Crear un AccessToken en el espacio de nombres de la base de datos

Ahora crea un AccessToken en el espacio de nombres `shared-database` para establecer el enlace desde la base de datos hasta tu espacio de nombres. El token debe llamarse `token-{username}`.

Extrae los detalles del grant y crea el AccessToken:

{blank}

[.copypaste]
****
URL=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.url}')
CODE=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.code}')
CA=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.ca}' | sed 's/^/    /')

cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-{username}
  namespace: shared-database
spec:
  url: "${URL}"
  code: "${CODE}"
  ca: |
${CA}
EOF
****

=== Exponer el servicio de base de datos

La red ya está configurada: tu espacio de nombres y el de la base de datos están conectados mediante un enlace cifrado. Sin embargo, tener una red no basta para acceder a la base de datos. Debes indicarle a Service Interconnect *qué servicio* debe exponer en tu espacio de nombres.

Aquí es donde entran en juego los Listeners y los Connectors. El Connector del lado de la base de datos ya está configurado (lo viste en el paso 0). Ahora debes crear un Listener coincidente de tu lado.

{empty} +

==== Paso 4: Crear un Listener para exponer la base de datos localmente

El Listener crea un servicio local en tu espacio de nombres que reenvía el tráfico a la base de datos PostgreSQL remota a través del enlace cifrado.

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: postgres-listener
  namespace: {username}-devspaces
spec:
  routingKey: postgres
  host: postgres
  port: 5432
EOF
****

IMPORTANT: `routingKey` debe coincidir con el valor configurado en el Connector del espacio de nombres `shared-database`. El equipo de la plataforma lo estableció como `postgres`.

Comprueba que el Listener esté listo:

=== Más allá de este ejercicio: Service Interconnect a escala

En este laboratorio conectaste dos espacios de nombres del mismo clúster: una configuración sencilla para demostrar los conceptos. En el mundo real, Service Interconnect demuestra su valor al conectar servicios en varios clústeres, regiones y proveedores de nube, todos ellos dentro de la misma malla segura.

Imagina una empresa minorista con tiendas en distintas regiones, cada una con servicios basados en IA. Los sitios edge recopilan datos de entrenamiento y ejecutan inferencias con modelos implementados localmente. Los centros de datos locales redundantes se encargan del trabajo pesado: entrenan modelos nuevos de IA y aprendizaje automático y envían las versiones actualizadas a las tiendas. Los hubs regionales agregan el tráfico de los sitios edge cercanos antes de reenviarlo al núcleo.

Cada sitio edge envía datos de entrenamiento al núcleo y recibe los modelos actualizados. Varios enlaces entre sitios ofrecen enrutamiento redundante: si una ruta falla, el tráfico fluye por otra. Los hubs añaden otra capa de resiliencia: si el hub de Frankfurt deja de funcionar, los sitios edge pueden redirigir el tráfico a través de Singapur. Los centros de datos redundantes garantizan que el flujo de trabajo de IA siga disponible incluso durante tareas de mantenimiento o interrupciones.

Aquí se aplica el mismo patrón de dos etapas que acabas de aprender: los Sites y los enlaces forman la red, mientras que los Listeners y los Connectors exponen los servicios específicos en cada extremo. La diferencia está en la escala: en lugar de dos espacios de nombres en un clúster, abarca varias regiones, hubs y centros de datos. Sin embargo, los componentes básicos son idénticos.
