= Firma de tus commits
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

Cada commit cuenta una historia, pero ¿cómo sabes si es cierta? La autoría de un commit se puede falsificar con un solo comando `git config`. El acceso al repositorio puede verse comprometido. Las claves SSH o GPG se pueden perder, robar o compartir. La firma de código tradicional depende de pares de claves de larga duración que los desarrolladores deben administrar, rotar y proteger, y muchos simplemente no lo hacen.

La **firma sin claves de Sigstore** aquí, con **Red Hat Trusted Artifact Signer (RHTAS)**, implementado como un componente de infraestructura del clúster, resuelve este problema al vincular la firma con la *identidad* del desarrollador en lugar de con un par de claves. Cuando firmas un commit, te autenticas con el proveedor de identidad de tu organización (en nuestro caso, Keycloak SSO). Fulcio (la autoridad de certificación de RHTAS) emite un certificado de corta duración, la firma se registra en el registro de transparencia de Rekor y el certificado caduca en cuestión de minutos. No hay claves que administrar, perder ni rotar.

En esta sección, confirmarás el arreglo de vulnerabilidades que acabas de realizar y lo firmarás con tu identidad.

image::m02-devspaces-sync-changes.png[Botón Sync Changes en el panel Source Control,link=self,window=blank,width=300]

Haz clic en la insignia para ver los detalles del certificado: observa que **Certificate Issuer** muestra `CN=CISO-office,O=Parasol`. === ¿Por qué es importante?

* **Responsabilidad**: Cada commit está vinculado criptográficamente a una identidad verificada, no solo a un nombre en la configuración de Git.
* **Evidencia de alteración**: Si alguien modifica un commit firmado, la firma deja de ser válida.
* **Sin administración de claves**: Los desarrolladores no necesitan generar, almacenar ni rotar claves de firma.
* **Transparencia**: Cada firma se registra en un registro público de transparencia (Rekor), lo que crea un historial auditable.
* **Control de la canalización**: Las etapas posteriores de la canalización verificarán que los commits se hayan firmado antes de compilar.

=== ¿Cómo se hizo?

Para que el ejercicio sea fácil de leer, añadimos los detalles a continuación. Expande la sección para ver cómo se hizo.

.**Abre para ver los detalles de implementación**
[%collapsible]
====
Git se configuró para usar **gitsign** como programa de firma. Esto se configura automáticamente cuando se inicia el espacio de trabajo de Dev Spaces, mediante el comando `postStart` del devfile:

[source,bash]
----
git config --global gpg.format x509
git config --global gpg.x509.program gitsign
git config --global commit.gpgsign true
git config --global gitsign.fulcio "https://fulcio-server-trusted-artifact-signer.{subdomain}"
git config --global gitsign.rekor "https://rekor-server-trusted-artifact-signer.{subdomain}"
git config --global gitsign.issuer "https://sso.{subdomain}/realms/sso"
----

El **flujo sin claves de Sigstore** funciona de la siguiente manera:

. El desarrollador inicia un commit.
. Gitsign redirige al proveedor OIDC (Keycloak) para la autenticación.
. Tras la autenticación, gitsign solicita un certificado de corta duración a **Fulcio** (la autoridad de certificación).
. Fulcio emite un certificado que incluye el correo electrónico del desarrollador como Subject Alternative Name.
. Gitsign firma el commit con este certificado.
. La firma se registra en **Rekor** (el registro de transparencia) para que pueda auditarse.
. El certificado caduca en cuestión de minutos, pero la entrada de Rekor demuestra que la firma era válida en el momento de firmar.

Como Dev Spaces se ejecuta en un contenedor sin navegador local, el daemon **gitsign-credential-cache** gestiona el flujo OIDC mostrando un código de verificación que el desarrollador pega en una terminal. En un IDE local, gitsign abriría el navegador directamente.
====
