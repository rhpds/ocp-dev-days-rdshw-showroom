= Moving to the Next Stages
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

Your sandbox image is clean -- vulnerabilities addressed, base image hardened, commit signed. Now it is time to move your changes through the secured pipeline stages: merge request check, post-merge build, and tag-based promotion to production.

Unlike the sandbox, these pipelines **enforce** security policies. Unsigned commits, policy violations, and missing approvals will block promotion.

[#section-1]
== Section 1: Merge Request

=== Exercise 1: Create a Merge Request

. Open GitLab and navigate to your sandbox branch in the `parasol-insurance-secured` repository.
+
You can find it quickly by clicking **View Source** on your sandbox component in Developer Hub.
+
image::m02-rhdh-sandbox-view-source.png[View Source on the sandbox component page,link=self,window=blank,width=700]

. Click **Create merge request** (or navigate to **Merge Requests** → **New merge request**).
+
image::m02-gitlab-create-mr.png[Create merge request button in GitLab,link=self,window=blank,width=700]

+
image::m02-gitlab-new-mr-form.png[New merge request form showing source and target branches,link=self,window=blank,width=700]

. Give the merge request a descriptive title:
+
[source,role="copypaste"]
----
Sec-fix done, security posture improved
----
+
Remove the "Description" and click **Create merge request**.

=== Exercise 2: Watch the MR check pipeline

. After creating the merge request, a check pipeline is triggered automatically. "can this build in preprod, will it pass, does it adhere to our standards?" If this fails, the branch with the changes cannot be merged. This is the **merge request check pipeline** -- it runs in the Parasol secured build namespace, not in your sandbox.
+
image::m02-gitlab-mr-pipeline-running.png[MR check pipeline running with merge blocked,link=self,window=blank,width=700]

. Open the pipeline view in GitLab and click on one of the tasks. It will open the MR Check Pipeline Run in Developer Hub.
+
image::m02-gitlab-mr-pipeline-jobs.png[GitLab MR pipeline showing commit verification and ACS jobs,link=self,window=blank,width=700]

. Notice the component -- this is `Parasol Insurance (Secured)`, not your sandbox anymore.
+
image::m02-rhdh-mr-check-pipeline.png[MR check pipeline in Developer Hub on Parasol Insurance Secured,link=self,window=blank,width=700]

. The MR check pipeline:
* **Verifies the commit signature** -- with `ENFORCE=true`, unsigned commits will **fail the pipeline**
* **Builds the image** from the MR branch
* **Scans and checks** the image against ACS policies
* **Reports results** back to GitLab as commit statuses and a detailed MR comment

. Wait for the pipeline to complete.

. Go back to the merge request page in GitLab 
* The "Merge" button has been activated, so you can merge - but before you do 
* Scroll down for the latest entry in the Activity where a **🔀 Merge Request Check Results** comment is posted with signature status, ACS policy results, and vulnerability counts
* For a succeeded pre-check, this is not as interesting as checking what went wrong and how to fix it. For you, this is informational (since it succeeded)
+
image::m02-gitlab-mr-ready-to-merge.png[Merge request ready to merge with pipeline passed,link=self,window=blank,width=700]
+
image::m02-gitlab-mr-results.png[Merge request check results showing signature and ACS validation,link=self,window=blank,width=700]

=== Exercise 3: Merge the request

. If all checks pass, the **Merge** button becomes available.
+
NOTE: If the pipeline failed (e.g., unsigned commit), the merge is blocked. GitLab is configured with `onlyMergeWhenPipelineSucceeds` to enforce this.

. Click **Merge**.
+
This triggers the **post-merge build pipeline** -- the **__final image__** is built from `main`, signed & attested by Tekton Chains, stored in Quay and deployed to the preprod environment.
+
image::m02-rhdh-post-merge-pipeline.png[Post-merge build pipeline in Developer Hub,link=self,window=blank,width=700]

== Section 2: Promote to production

The post-merge build created a signed image from the `main` branch. To promote it to production, you create a **Git tag** -- this triggers the tag-promote pipeline.

=== Exercise 1: Create a tag

. In GitLab, navigate to **Repository** → **Tags**.

. Click **New tag**.

. Enter a tag name (for example, `v2.0`) and select the `main` branch as the source.
+
image::m02-gitlab-create-tag.png[Creating a tag in GitLab,link=self,window=blank,width=700]

. Click **Create tag**.

=== Exercise 2: Watch the tag-promote pipeline

. The tag triggers the **tag-promote pipeline**. This pipeline:
* Retrieves the image SHA from the registry
* Runs **Conforma/Enterprise Contract validation** against the image's attestation
* Generates an **SBOM** and uploads it to TPA
* Copies the image to a tagged version in the registry
* Opens a **merge request** on the GitOps manifests repository to update the production deployment

. Go to the **Parasol Insurance (Secured)** component in Developer Hub and click the **CI** tab.
+
Look for the `parasol-insurance-secured-tag-promote` pipeline run.
+
image::m02-rhdh-tag-promote-failed.png[Tag promote pipeline failed in Developer Hub showing ec-validate failure,link=self,window=blank,width=700]

. **The pipeline will fail.** Open the pipeline output to see why.
+
image::m02-rhdh-tag-promote-view-output.png[View output button on the failed tag-promote pipeline,link=self,window=blank,width=700]
+
image::m02-rhdh-ec-validation-failed.png[Enterprise Contract validation showing failed approval rule,link=self,window=blank,width=700]

=== Exercise 3: Understand the Conforma policy violation

. The **Conforma (ec)** validation checks the image's signed attestation against a set of policies. You should see:
* ✅ **Image signature check** -- the image is signed by Tekton Chains
* ✅ **Attestation signature check** -- the attestation is signed and valid
* ✅ **Commit must be signed** -- the SLSA attestation proves the commit was signed
* ✅ **ACS checks passed** -- image scan and policy check results are in the attestation
* ✅ **SonarQube quality gate** -- code quality metrics are in the attestation
* ❌ **Parasol Release Approved** -- no release approval attestation found
+


. The pipeline correctly blocks promotion because the image has not been approved for release. There is no **signed attestation of a release approval** attached to the image

=== Why is this important?

The image deployed to production now carries a complete **SLSA provenance chain**:

* **Signed commit** -- traceable to a verified developer identity
* **SLSA attestation** -- proving the build pipeline ran, which tasks executed, and what results they produced
* **ACS scan results** -- vulnerability assessment baked into the attestation
* **SonarQube results** -- code quality metrics in the attestation
* **Signed approval** -- explicit human authorization for the release
* **SBOM** -- a complete inventory of components in the image, stored in TPA for ongoing vulnerability matching

This is not just a checkbox exercise -- every piece of evidence is cryptographically signed and independently verifiable.

=== How was it done?

To keep the exercise readable, we have added the details below. Expand to read how it was done.

.**Open to view implementation details**
[%collapsible]
====
**Tekton Chains** automatically signs pipeline artifacts using Sigstore keyless signing:

* After each pipeline run, Chains requests a short-lived certificate from **Fulcio** using the pipeline service account's identity
* It creates a **SLSA provenance attestation** containing all task results
* The attestation and signature are recorded in **Rekor** (transparency log) and attached to the image in the registry

**Conforma (Enterprise Contract)** validates the attestation against a set of Rego policies stored in the {gitlab_url}/parasol/conforma-policies[`conforma-policies` repository on GitLab^]. The policies in the `parasol-software-supply-chain` bundle check:

* Required tasks were executed (verify-commit-signature, acs-image-scan, acs-image-check, sonar-scan)
* Commit signature status is `SIGNED` (not unsigned or bot commit)
* ACS policy check passed
* SonarQube quality gate passed
* A signed release approval attestation exists on the image

image::m02-gitlab-conforma-policies.png[Conforma policies repository on GitLab,link=self,window=blank,width=700]

The **approval attestation** is a custom in-toto attestation with predicate type `https://parasol-insurance.com/releases/v1`. It is signed by the approver's identity (via Fulcio) and attached to the image alongside the Chains attestation.

If you want to inspect the signed attestations associated with the image now in production, go back to the **Release Approval** app (via the **Parasol Insurance (Secured)** component on Developer Hub):

image::m02-rhdh-release-approval-link.png[Release Approval link on the Parasol Insurance Secured component,link=self,window=blank,width=400]

Click on a tag to inspect the signed attestations associated with that image:

image::m02-approval-inspect-attestations.png[Inspect Attestations by clicking on a tag,link=self,window=blank,width=500]

Here you can see the signer identity for the custom attestation as well as the auto-generated attestations signed by Tekton Chains:

image::m02-approval-attestation-details.png[Attestation details showing Release Approval and SLSA Provenance with signer identities,link=self,window=blank,width=700]

In the **Attestation Detail** section you can inspect the attestation stored with the image:

image::m02-approval-attestation-json.png[Attestation Detail showing the in-toto statement with predicate and subject,link=self,window=blank,width=700]

The **SBOM** is generated using **syft** and uploaded to TPA with labels identifying the developer and version tag. TPA continuously matches SBOMs against ingested vulnerability data, providing ongoing visibility into the security posture of deployed images.
