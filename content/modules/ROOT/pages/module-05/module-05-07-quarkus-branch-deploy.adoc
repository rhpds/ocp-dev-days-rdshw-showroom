== Exercise 2: Review the migrated code

Walk the same classes you touched earlier and compare them to the Quarkus implementations.

=== Packaging and dependencies

. Open `pom.xml` on the `quarkus` branch. Note the shift from an EAP / Java EE WAR toward Quarkus:
* Packaging is **`jar`** (not `war`)
* Dependencies come from the **Quarkus BOM** (`quarkus-rest`, `quarkus-hibernate-orm`, `quarkus-messaging`, `quarkus-scheduler`, JDBC drivers, and so on)
* There is no `jboss-eap-javaee8` BOM or `javax.*` EJB / JMS API stack

. Open `src/main/resources/application.properties`. Observe:
* **Dev** profile uses in-memory **H2**
* **`%prod`** profile uses **PostgreSQL** via `POSTGRESQL_*` environment variables (what OpenShift will inject)

=== Messaging: `EmailIntakeMDB`

. Open `src/main/java/com/parasol/mdb/EmailIntakeMDB.java`.
+
Confirm the migration outcomes from Section 4:
* `@ApplicationScoped` instead of `@MessageDriven`
* `@Inject` instead of `@EJB`
* `@Incoming("email-intake")` instead of JMS `MessageListener` / activation config
* `jakarta.*` imports

=== Business services: `ClaimService`

. Open `src/main/java/com/parasol/ejb/ClaimService.java`.
+
Confirm the migration outcomes from Section 6:
* `@ApplicationScoped` + `@Transactional` instead of `@Stateless`
* `@Inject EntityManager` instead of `@PersistenceContext`
* No `javax.ejb` usage

=== Scheduling: `EmailGeneratorBean`

. Open `src/main/java/com/parasol/ejb/EmailGeneratorBean.java`.
+
Note how the old EJB timer / JMS producer path became Quarkus-native:
* `@Scheduled(...)` instead of `TimerService` / `@Timeout`
* `@Channel("email-intake") Emitter<String>` instead of JMS `ConnectionFactory` / `Queue`
* Still `@ApplicationScoped`, feeding the same `email-intake` channel the MDB consumes

=== REST layer

. Open `ClaimsResource` and `InboxResource`. Confirm CDI `@Inject` of services (no `@EJB`) and `jakarta.ws.rs` APIs.

[cols="2,2,2"]
|===
| Concern | Legacy (`main`) | Quarkus branch

| Packaging | WAR + EAP BOM | JAR + Quarkus BOM
| APIs | `javax.*` | `jakarta.*`
| Claims service | `@Stateless` EJB | `@ApplicationScoped` + `@Transactional`
| Email intake | JMS `@MessageDriven` | `@Incoming("email-intake")`
| Email generator | EJB timer + JMS | `@Scheduled` + `@Channel` Emitter
| Datasource (prod) | `java:jboss/datasources/...` | Quarkus JDBC + env vars
|===

== Exercise 4: Deploy to OpenShift

Deploy from the `quarkus` branch using the manifests under `openshift/` and a cluster-side binary Docker build. These steps assume `oc` is logged in and a project/namespace is selected (`oc project`).

=== Provision PostgreSQL

. Create an ephemeral PostgreSQL instance for the demo:
+
[.console-input]
[source,bash,role="execute"]
----
oc new-app --template=postgresql-ephemeral \
  -p DATABASE_SERVICE_NAME=parasol-db \
  -p POSTGRESQL_USER=parasol \
  -p POSTGRESQL_PASSWORD=parasol \
  -p POSTGRESQL_DATABASE=parasol
----

. Wait until the database is ready:
+
[.console-input]
[source,bash,role="execute"]
----
oc rollout status deploymentconfig/parasol-db 2>/dev/null \
  || oc rollout status deployment/parasol-db
oc get pods -l name=parasol-db
----

=== Build the Quarkus application

. Package the app locally (or in the Dev Spaces terminal):
+
[.console-input]
[source,bash,role="execute"]
----
mvn clean package -DskipTests
----
+
This produces `target/quarkus-app/`.

. Assemble a binary build context and start an OpenShift Docker build:
+
[.console-input]
[source,bash,role="execute"]
----
rm -rf /tmp/parasol-build
mkdir -p /tmp/parasol-build
cp src/main/docker/Dockerfile.jvm /tmp/parasol-build/Dockerfile
cp -R target/quarkus-app /tmp/parasol-build/

oc new-build --name=parasol-insurance --binary --strategy=docker -l app=parasol-insurance
oc start-build parasol-insurance --from-dir=/tmp/parasol-build --follow
----

=== Apply deployment manifests

. Deploy the application (image namespace is substituted from your current project). The Deployment maps Secret `parasol-db` into the `POSTGRESQL_*` variables expected by the **`%prod`** profile:
+
[.console-input]
[source,bash,role="execute"]
----
NS=$(oc project -q)
sed "s|REPLACE_NAMESPACE|${NS}|g" openshift/deployment.yaml | oc apply -f -
oc apply -f openshift/service.yaml
oc apply -f openshift/route.yaml
oc rollout status deployment/parasol-insurance
----

. Get the Route URL and open it in the browser:
+
[.console-input]
[source,bash,role="execute"]
----
ROUTE=$(oc get route parasol-insurance -o jsonpath='{.spec.host}')
echo "https://${ROUTE}/"
----

. Verify the APIs from the terminal:
+
[.console-input]
[source,bash,role="execute"]
----
curl -sk "https://${ROUTE}/api/claims"
curl -sk "https://${ROUTE}/api/inbox"
----

. In the OpenShift console, open your project **Topology** (or **Workloads → Deployments**) and confirm `parasol-insurance` (and `parasol-db`) are running. Review the Deployment env vars and the Route host.

== Exercise 5: Review what changed in production config

. Re-open `openshift/deployment.yaml` and relate it to `application.properties` `%prod` settings:
* `POSTGRESQL_HOST=parasol-db`
* Credentials from Secret `parasol-db`
* HTTP probes on `/api/claims`

. Contrast this with the legacy EAP approach (`java:jboss/datasources/ParasolDS`, `jboss-all.xml` JMS queue definitions). Quarkus moves runtime wiring into **application config + Kubernetes env**, which is easier to GitOps and promote across environments.

== What we learnt

* The **`quarkus`** branch is the completed migration target for the patterns you practiced with MTA / DLS.
* Messaging, CDI services, scheduling, and REST all use Quarkus / MicroProfile idioms (`@Incoming`, `@Channel`, `@Scheduled`, `@ApplicationScoped`).
* Local **`quarkus:dev`** (H2) is ideal for quick UI verification; **OpenShift** uses PostgreSQL via the `%prod` profile.
* Container deploy is a standard binary build + Deployment / Service / Route — no EAP-specific subsystem XML required.
