== Enabling Database Connectivity

The integration flow needs access to the database, but it isn't reachable yet. Let's find out why, and enable the connection.

NOTE: This exercise uses a single cluster to keep things focused, but Service Interconnect is designed for far more than a network policy can handle — multi-site meshes spanning clusters, regions, and cloud providers. A brief real-world example at the end shows it in that broader context.

{empty} +

=== Why can't you reach the database?

The backend database is hosted in an isolated namespace (`shared-database`) with strict network policies — no direct access is allowed from other namespaces.

=== Bridging namespaces with Service Interconnect

NOTE: {rhsi} is a supported offering built from the upstream https://skupper.io[Skupper.io,window=_blank] open-source project.

{rhsi} solves this by creating encrypted application-level connections between namespaces — without requiring VPNs, firewall rules, or exposing services to the public network.

Once configured, a local service is created in your namespace that transparently forwards traffic to the remote database:

{blank}

[.mermaid-hints-simple]
****
S2 | Site | The foundation of the Skupper network. Each participating namespace runs a Site. Sites discover each other through AccessGrants and AccessTokens. +
S1 | Site | The foundation of the Skupper network. Each participating namespace runs a Site. Sites discover each other through AccessGrants and AccessTokens. +
Grant | AccessGrant | Created on the receiving side. It generates credentials that allow a remote Site to connect. Think of it as an invitation to join the network. +
Token | AccessToken | Created on the connecting side using the grant details. It establishes the encrypted link between two Sites. +
Listener | Listener | Exposes a remote service locally in your namespace. It matches a Connector on the other side by routing key, making the remote service appear as a local one. +

****

TIP: Hover over each component in the diagram to learn what it does.

NOTE: The database lives in a secure, air-tight environment — no inbound ports are exposed. To keep it that way, the link is initiated *from* the database side *outward* to your site. This is why you create an AccessGrant on your side: it gives the database site permission to connect to you and establish a bidirectional communication link. Its environment never opens an entrypoint that could be exploited.

=== What you will do

Every Service Interconnect setup follows two stages: first you *establish the network* — the secure mesh that connects your environments — then you *expose services* through it. Once the network is in place, adding a new service is just a matter of pairing a Listener with a Connector — no network changes needed.

==== Step 2: Create an AccessGrant

Before jumping in, remember that the link is initiated *from* Site(1) (database) *to* Site(2) (yours). Here's how the grant and token work together to make that happen:

{blank}

[.mermaid]
----
sequenceDiagram
    actor A as Admin<br/>(You)
    participant S2 as Site(2)
    participant S1 as Site(1)

    A-->>S2: Create AccessGrant

    Note over S2: AccessGrant

    A-->>S1: Create AccessToken

    Note over S1: AccessToken

    S1-->>S2: Redeem token
    S2-->>S1: Transfer link details
    S1->>S2: Create link

    Note over S2,S1: 🔒 secure link established
----

You create an AccessGrant on your Site(2) and an AccessToken on Site(1). The database site then redeems the token to establish a secure link back to you.

{blank}

Now, create the AccessGrant:

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessGrant
metadata:
  name: grant-{username}
  namespace: {username}-devspaces
spec:
  redemptionsAllowed: 1
  expirationWindow: 168h
EOF
****

==== Step 3: Create an AccessToken in the Database Namespace

Now create an AccessToken in the `shared-database` namespace to establish the link from the database to your namespace. The token must be named `token-{username}`.

Extract the grant details and create the AccessToken:

{blank}

[.copypaste]
****
URL=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.url}')
CODE=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.code}')
CA=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.ca}' | sed 's/^/    /')

cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-{username}
  namespace: shared-database
spec:
  url: "${URL}"
  code: "${CODE}"
  ca: |
${CA}
EOF
****

IMPORTANT: The AccessToken name *must* follow the pattern `token-<your-username>`. Any other name will be rejected.

After a few moments, a *Link* resource is automatically created in `shared-database`. Verify:

[.copypaste]

****

=== Expose the database service

The network is now in place — your namespace and the database namespace are connected through an encrypted link. But having a network alone doesn't give you access to the database. You still need to tell Service Interconnect *which service* to expose into your namespace.

This is where Listeners and Connectors come in. The Connector on the database side is already configured (you saw it in Step 0). Now you need to create a matching Listener on your side.

{empty} +

==== Step 4: Create a Listener to Expose the Database Locally

The Listener creates a local service in your namespace that forwards traffic to the remote PostgreSQL database through the encrypted link.

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: postgres-listener
  namespace: {username}-devspaces
spec:
  routingKey: postgres
  host: postgres
  port: 5432
EOF
****

IMPORTANT: The `routingKey` must match the one configured on the Connector in the `shared-database` namespace. The platform team set it to `postgres`.

=== Beyond this exercise: Service Interconnect at scale

In this lab you connected two namespaces on the same cluster — a simple setup to demonstrate the concepts. In the real world, Service Interconnect shines when connecting services across multiple clusters, regions, and cloud providers — all sharing the same secure mesh.

Consider a retail organization with stores across different regions, each running AI-powered services. Edge sites collect training data and run inference against locally deployed models. Redundant on-prem data centers handle the heavy lifting — training new AI/ML models and pushing updated versions back to the stores. Regional hubs aggregate traffic from nearby edges before forwarding it to the core.

Each edge site pushes training data to the core and pulls updated models back. Multiple links between sites provide redundant routing — if one path fails, traffic flows through another. Hubs add a further layer of resilience: if the Frankfurt hub goes down, edges can reroute through Singapore. Redundant data centers ensure the AI pipeline stays available even during maintenance or outages.

The same two-stage pattern you just learned applies here: Sites and links form the network, while Listeners and Connectors expose the specific services at each end. The difference is scale — instead of two namespaces on one cluster, this spans multiple regions, hubs, and data centers. But the building blocks are identical.
