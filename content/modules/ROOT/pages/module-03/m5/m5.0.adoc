=== The Scenario

In the previous labs, you built an AI agent that resolves customer support issues through natural language. The agent queries the database, updates records, and regenerates invoices, all from within the chat interface.

Now you want to extend it with a new capability: **customer profile analysis**. When a support agent asks about a customer, the AI analyzes their data and returns a structured summary. Two tiers of analysis are available:

* **Gold** -- full purchase history, spending patterns, and loyalty status.
* **Silver** -- recent orders and basic profile information.

Gold consumes more tokens because the analysis is deeper and the response is richer. Silver is lighter. The system is designed with a fallback strategy: if the Gold tier's token budget is exhausted, the service falls back to Silver. If Silver is also exhausted, the request is deferred.

But before any of this works, you need governance. Who can access the LLM endpoint? How many tokens can each tier consume? Without controls, there is nothing stopping unchecked consumption from burning through the organization's API budget.

In this lab, you'll place a **governance layer** in front of the LLM endpoint using link:https://www.redhat.com/en/technologies/cloud-computing/connectivity-link[*_Red Hat Connectivity Link_*,window=_blank]. You'll implement two policies:

* **AuthPolicy** -- Control _who_ can access the endpoint using API key authentication and group-based authorization.
* **TokenRateLimitPolicy** -- Control _how much_ each tier can consume by enforcing rate limits based on actual token usage.

{empty} +

=== Why Connectivity Link?

This is exactly the kind of problem _Red Hat Connectivity Link_ was designed for. Built on the link:https://kuadrant.io/[_Kuadrant_ project,window=_blank], it brings AI-aware governance to *Kubernetes*:

* **Token-aware rate limiting** -- limits are based on actual tokens consumed, not request counts. This is what makes tiered AI services viable: each tier gets its own token budget, enforced at the gateway.
* **Zero code changes** -- policies are applied at the infrastructure level. Your AI agent and integration code stay untouched.
* **Kubernetes-native** -- policies are standard CRDs, applied with `oc apply`, stored in Git, reviewed in PRs. No separate management console or vendor control plane.
* **Composable** -- one policy extracts identity, another uses it for per-tier token budgets. They layer on top of each other declaratively.

These capabilities come from how Connectivity Link builds on the _Kubernetes Gateway API_ standard. Before you start configuring policies, let's look at the Gateway API model.

{empty} +

=== The Gateway API Model

Connectivity Link layers on top of the _Kubernetes Gateway API_, the standard for managing traffic routing in _Kubernetes_. Understanding this model will make the exercises that follow intuitive.

Here are the building blocks:

* **GatewayClass + Gateway** -- owned by the platform team. Defines _how_ traffic enters the cluster. Already provisioned for you.
* **HTTPRoute** -- owned by the platform or development team. Defines _where_ your traffic goes (in this case, the LLM API).
