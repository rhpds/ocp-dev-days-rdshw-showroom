== データベース接続を有効にする

統合フローからデータベースにアクセスする必要がありますが、まだ接続できません。原因を確認し、接続を有効にしましょう。

NOTE: この演習では要点に集中できるよう単一の cluster を使用しますが、Service Interconnect は network policy では対応しきれない、複数の cluster、リージョン、クラウドプロバイダーにまたがるマルチサイト mesh に対応するよう設計されています。最後に、より広い用途を示す実例を簡単に紹介します。

{empty} +

=== データベースに接続できないのはなぜですか？

バックエンドデータベースは、厳格な network policy が適用された隔離 namespace (*shared-database*) でホストされています。他の namespace からの直接アクセスは許可されていません。

=== Service Interconnect で namespace 間を接続する

{rhsi}（オープンソースプロジェクト https://skupper.io[Skupper.io,window=_blank] を基に構築）は、namespace 間にアプリケーションレベルの暗号化接続を作成することでこの問題を解決します。VPN や firewall rule は不要で、サービスをパブリックネットワークに公開する必要もありません。

設定が完了すると、namespace 内に local service が作成され、remote database に traffic が透過的に転送されます。

****

Grant | AccessGrant | 接続を受け入れる側で作成します。remote Site が接続するための credential を生成します。ネットワークへの招待状と考えてください。 +
Token | AccessToken | grant の詳細を使って接続元で作成します。2 つの Site 間に暗号化 link を確立します。 +
Listener | Listener | namespace 内で remote service を local に公開します。routing key で相手側の Connector と対応付け、remote service を local service のように扱えるようにします。 +
Connector | Connector | local service を Skupper network に接続します。service を公開し、他の namespace にある対応する Listener からアクセスできるようにします。 +
SVC2 | Service (自動作成) | Listener を作成すると、Service Interconnect がローカル Kubernetes service を自動作成します。アプリケーションはデータベースがローカルにあるかのようにこの service に接続します。
****

TIP: 図の各構成要素にカーソルを合わせると、その役割が表示されます。

データベースは安全に隔離された環境にあり、受信 port は公開されていません。それを維持するため、link はデータベース側 *から* あなたの Site *へ向けて* 開始します。このため、あなた側で AccessGrant を作成します。これにより、データベース Site があなたに接続し、双方向の通信 link を確立する許可を得ます。悪用される可能性のある入口を、その環境で開く必要はありません。

=== この演習で行うこと

Service Interconnect の構成はすべて 2 段階で行います。まず、環境を接続する secure mesh で *network を確立* し、次にその network 経由で *service を公開* します。network の準備ができたら、新しい service の追加は Listener と Connector を組み合わせるだけです。network の変更は必要ありません。

この演習では、次の手順になります。

*ネットワークを確立* — namespace 間にセキュアリンクを作成します。

[start=0]
. `shared-database` namespace には *Site* がすでにあります _(事前設定済み)_
. `linkAccess` を有効にして、namespace に *Site* を作成します
. データベース namespace が接続できるように *AccessGrant* を生成します
. link を確立するため、データベース namespace に *AccessToken* を作成します

*データベース service を公開* — remote database に local（`{username}-devspaces` 内）からアクセスできるようにします。

[start=4]
. Skupper network と port `5432` の PostgreSQL を接続する *Connector* はすでにあります _(事前設定済み)_
. remote database を local service として公開する *Listener* を作成します

==== 手順 3: データベース namespace に AccessToken を作成する

データベースから namespace への link を確立するため、`shared-database` namespace に AccessToken を作成します。token 名は `token-{username}` にする必要があります。

grant の詳細を取り出して、AccessToken を作成します。

{blank}

[.copypaste]
****
URL=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.url}')
CODE=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.code}')
CA=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.ca}' | sed 's/^/    /')

cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-{username}
  namespace: shared-database
spec:
  url: "${URL}"
  code: "${CODE}"
  ca: |
${CA}
EOF
****

しばらくすると、`shared-database` に *Link* resource が自動作成されます。確認しましょう。

{blank}

[.copypaste]

****

=== データベース service を公開する

network の準備ができ、namespace とデータベース namespace が暗号化 link で接続されました。しかし、network だけではデータベースにアクセスできません。Service Interconnect に、namespace へ公開する *service* を指定する必要があります。

ここで Listener と Connector を使います。データベース側の Connector はすでに設定済みです（Step 0 で確認しました）。次に、あなた側で対応する Listener を作成します。

{empty} +

==== 手順 4: Listener を作成してデータベースを local に公開する

Listener は namespace 内に local service を作成し、暗号化 link 経由で remote PostgreSQL データベース に traffic を転送します。

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: postgres-listener
  namespace: {username}-devspaces
spec:
  routingKey: postgres
  host: postgres
  port: 5432
EOF
****

IMPORTANT: `routingKey` は `shared-database` namespace の Connector に設定された値と一致する必要があります。platform team は `postgres` に設定しています。

Listener の準備ができたことを確認します。

{blank}

[.copypaste]

oc get listener postgres-listener -n {username}-devspaces
****

=== この演習の先へ：大規模環境での Service Interconnect

この lab では、概念を説明するために同じ cluster 上の 2 つの namespace を接続しました。実環境で Service Interconnect の真価が発揮されるのは、複数の cluster、リージョン、クラウドプロバイダーにまたがる service を、同じ secure mesh で接続するときです。

各地域に店舗があり、それぞれで AI を活用した service を実行する小売企業を考えてみましょう。edge site では学習データを収集し、local に deploy された model で inference を実行します。冗長化された on-prem data center が、新しい AI/ML model の学習や更新版の店舗への配信といった大規模な処理を担います。地域 hub は、近隣の edge から traffic を集約して core に転送します。

各 edge site は学習データを core に送信し、更新済み model を受信します。Site 間に複数の link を設けて冗長な routing を実現するため、経路の 1 つに障害が発生しても、traffic は別の経路を流れます。hub はさらに resilience を高めます。Frankfurt hub が停止した場合、edge は Singapore 経由で再 routing できます。冗長化された data center により、メンテナンス中や障害時も AI pipeline の可用性を保てます。
