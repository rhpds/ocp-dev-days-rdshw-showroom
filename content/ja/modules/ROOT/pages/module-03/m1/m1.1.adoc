== データベース接続を有効にする

統合フローはデータベースにアクセスする必要がありますが、まだ到達できません。理由を確認し、接続を有効にしましょう。

NOTE: この演習では、焦点を絞るために単一クラスターを使用しますが、Service Interconnect はネットワークポリシーでは対応しきれない規模を想定しています。複数のクラスター、リージョン、クラウドプロバイダーにまたがるマルチサイト・メッシュです。最後に短い実世界の例で、より広い文脈を示します。

{empty} +

=== なぜデータベースに到達できないのですか？

バックエンドのデータベースは、厳格なネットワークポリシーを持つ隔離された namespace（*shared-database*）でホストされています。ほかの namespace からの直接アクセスは許可されていません。

=== Service Interconnect で namespace をつなぐ

{rhsi}（オープンソースプロジェクト https://skupper.io[Skupper.io,window=_blank] を基に構築）を使うと、VPN や firewall ルール、サービスの public network への公開を必要とせずに、namespace 間で暗号化されたアプリケーションレベルの接続を作成できます。

設定すると、あなたの namespace にローカル service が作成され、リモートのデータベースへトラフィックを透過的に転送します。

[.mermaid-hints-simple]
****
S2 | Site | Skupper ネットワークの基盤です。参加する各 namespace は Site を実行します。Site は AccessGrant と AccessToken を通じて互いを見つけます。 +
S1 | Site | Skupper ネットワークの基盤です。参加する各 namespace は Site を実行します。Site は AccessGrant と AccessToken を通じて互いを見つけます。 +
Grant | AccessGrant | 受信側で作成されます。リモート Site が接続できるようにする資格情報を生成します。ネットワークへの招待状のようなものだと考えてください。 +
Token | AccessToken | grant の詳細を使って接続側で作成されます。2 つの Site 間の暗号化リンクを確立します。 +
Listener | Listener | あなたの namespace にあるリモート service をローカルに公開します。ルーティングキーで相手側の Connector と一致し、リモート service をローカルのように見せます。 +
Connector | Connector | ローカル service を Skupper ネットワークに接続します。ほかの namespace の一致する Listener が到達できるように service を公開します。 +
SVC2 | Service (auto-created) | Listener が作成されると、Service Interconnect は自動的にローカルの Kubernetes service を作成します。アプリケーションは、データベースがローカルにあるかのようにこの service に接続します。
****

TIP: 図の各 component にマウスオーバーすると、その役割を確認できます。

データベースは安全で、完全に閉じた環境にあります。inbound port は公開されていません。その状態を保つため、リンクはデータベース側 *から* あなたの site *へ* 発信されます。だからこそ、あなたの側で AccessGrant を作成します。これにより、データベース site にあなたへ接続し、双方向の communication link を確立する権限を与えます。その環境は、悪用されうる entrypoint を決して開きません。

{empty} +

=== あなたが行うこと

すべての Service Interconnect の設定は 2 段階で進みます。最初に *ネットワークを確立* し、つまり環境を接続する安全なメッシュを作成し、次にその上で *service を公開* します。ネットワークができれば、新しい service を追加するのは Listener と Connector をペアにするだけです。network change は不要です。

{empty} +

この演習では、それは次のようになります。

*ネットワークを確立する* — namespace 間に安全なリンクを作成します。

[start=0]
. *Site* はすでに `shared-database` namespace に存在します（事前設定済み）
. `linkAccess` を有効にした *Site* をあなたの namespace に作成します
. データベース namespace があなたに接続できるように *AccessGrant* を生成します
. リンクを確立するために、データベース namespace に *AccessToken* を作成します

*データベース service を公開する* — リモートのデータベースをローカルで利用可能にします（`{username}-devspaces` 内）。

[start=4]
. *Connector* はすでに Skupper ネットワークをポート `5432` の PostgreSQL に橋渡ししています（事前設定済み）
. リモートのデータベースをローカル service として公開するために *Listener* を作成します

=== ネットワークを確立する

最初のステップは、あなたの namespace とデータベース namespace の間に安全なネットワークを設定することです。これには Site、AccessGrant、AccessToken を作成します。これらが一緒になって、2 つの環境の間に暗号化リンクを確立します。

{empty} +

==== ステップ 1: あなたの namespace に Site を作成する

`linkAccess` を有効にした Site を作成します。これにより、あなたの namespace はデータベースからの着信接続を受け入れられる *待ち受け Site* になります。

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Site
metadata:
  name: {username}-site
  namespace: {username}-devspaces
spec:
  linkAccess: route
EOF
****

Site が ready になることを確認します。

==== ステップ 3: データベース namespace に AccessToken を作成する

次に、`shared-database` namespace に AccessToken を作成して、データベースからあなたの namespace へのリンクを確立します。token の名前は `token-{username}` でなければなりません。

grant の詳細を取り出して AccessToken を作成します。

{blank}

[.copypaste]
****
URL=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.url}')
CODE=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.code}')
CA=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.ca}' | sed 's/^/    /')

cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-{username}
  namespace: shared-database
spec:
  url: "${URL}"
  code: "${CODE}"
  ca: |
${CA}
EOF
****

数分後、`shared-database` に *Link* resource が自動作成されます。確認します。

{blank}

[.copypaste]
****
oc get link token-{username} -n shared-database
****

リンクの status が `Ready` になるまで待ちます。

=== データベース service を公開する

これでネットワークは整いました。あなたの namespace とデータベース namespace は、暗号化リンクで接続されています。しかし、ネットワークがあるだけではデータベースへアクセスできません。Service Interconnect に、*どの service を* あなたの namespace に公開するかをまだ伝える必要があります。

ここで Listener と Connector が登場します。データベース側の Connector はすでに設定済みです（ステップ 0 で確認しました）。次は、あなたの側に一致する Listener を作成します。

{empty} +

==== ステップ 4: データベースをローカルに公開する Listener を作成する

Listener は、暗号化リンクを通じてリモートの PostgreSQL データベースへトラフィックを転送するローカル service をあなたの namespace に作成します。

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: postgres-listener
  namespace: {username}-devspaces

=== この演習を越えて: 大規模環境での Service Interconnect

この lab では、同じクラスター上の 2 つの namespace を接続しました。概念を示すためのシンプルな構成です。実際の現場では、Service Interconnect は、複数のクラスター、リージョン、クラウドプロバイダーにまたがる service を接続するときに真価を発揮します。すべてが同じ安全なメッシュを共有します。

各地域に店舗があり、それぞれが AI を活用した service を実行している小売組織を考えてみましょう。エッジ site は学習データを収集し、ローカルに展開された model に対して推論を実行します。冗長なオンプレミス data center は重い処理を担当します。新しい AI/ML model の学習と、更新版を店舗へ戻す配信です。地域ハブは、近隣のエッジからのトラフィックを集約してから core に転送します。
