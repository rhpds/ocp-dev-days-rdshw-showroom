== データベース接続の有効化

統合フローではデータベースへのアクセスが必要ですが、まだ接続できません。その理由を確認し、接続を有効にしましょう。

NOTE: この演習では要点に集中するため単一クラスターを使用しますが、Service Interconnect はネットワークポリシーで対応できる範囲をはるかに超えた用途を想定して設計されています。クラスター、リージョン、クラウドプロバイダーにまたがるマルチサイトメッシュを構築できます。最後に、その広範な用途を示す実際の例を簡単に紹介します。

{empty} +

=== データベースに接続できないのはなぜですか？

バックエンドデータベースは、厳格なネットワークポリシーが適用された分離された namespace ( *shared-database* ) でホストされており、他の namespace から直接アクセスすることはできません。

=== Service Interconnect で namespace を接続する

{rhsi}（オープンソースプロジェクト https://skupper.io[Skupper.io,window=_blank] を基盤としています）は、namespace 間にアプリケーションレベルの暗号化接続を作成することでこの問題を解決します。VPN やファイアウォールルールは不要で、サービスをパブリックネットワークに公開する必要もありません。

設定すると、自分の namespace にローカルサービスが作成され、リモートデータベースにトラフィックが透過的に転送されます。

Grant | AccessGrant | 受信側で作成します。リモート Site が接続するための認証情報を生成します。ネットワークへの参加招待状と考えてください。 +
Token | AccessToken | 接続側で grant の詳細を使用して作成します。2つの Site 間に暗号化リンクを確立します。 +
Listener | Listener | namespace 内でリモートサービスをローカルに公開します。ルーティングキーを使って反対側の Connector と対応付け、リモートサービスをローカルサービスのように扱えるようにします。 +
Connector | Connector | ローカルサービスを Skupper ネットワークに接続します。サービスを公開し、他の namespace にある対応する Listener からアクセスできるようにします。 +
SVC2 | Service (自動作成) | Listener を作成すると、Service Interconnect がローカル Kubernetes サービスを自動作成します。データベースがローカルにあるかのように、このサービスにアプリケーションから接続できます。
****

TIP: 図の各コンポーネントにカーソルを合わせると、その役割を確認できます。

データベースは厳重に保護された環境にあり、インバウンドポートは公開されていません。その状態を維持するため、リンクはデータベース側 *から* 自分の Site *へ向けて* 開始されます。そのため、自分の側に AccessGrant を作成します。これにより、データベース側の Site に自分への接続と双方向通信リンクの確立を許可します。データベース環境で悪用される可能性のある入口を開くことはありません。

=== これから行うこと

Service Interconnect の設定はすべて2段階で行います。まず環境を接続するセキュアメッシュである *ネットワークを確立* し、次にそのネットワークを通じて *サービスを公開* します。ネットワークを構築した後は、Listener と Connector を組み合わせるだけで新しいサービスを追加でき、ネットワークを変更する必要はありません。

{empty} +

この演習では、次の作業を行います。

*ネットワークを確立* — namespace 間にセキュアリンクを作成します。

[start=0]
. `shared-database` namespace には *Site* がすでに存在します ( _事前設定済み_ )
. 自分の namespace に `linkAccess` を有効にした *Site* を作成します
. データベース namespace から接続できるように *AccessGrant* を生成します
. リンクを確立するため、データベース namespace に *AccessToken* を作成します

*データベースサービスを公開* — リモートデータベースをローカル（`{username}-devspaces` 内）からアクセスできるようにします。

[start=4]
. Skupper ネットワークとポート `5432` の PostgreSQL をすでに接続する *Connector* があります ( _事前設定済み_ )
. リモートデータベースをローカルサービスとして公開する *Listener* を作成します

==== ステップ 3: データベース namespace に AccessToken を作成する

データベースから自分の namespace へのリンクを確立するため、`shared-database` namespace に AccessToken を作成します。token の名前は `token-{username}` にする必要があります。

grant の詳細を抽出し、AccessToken を作成します。

{blank}

[.copypaste]
****
URL=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.url}')
CODE=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.code}')
CA=$(oc get accessgrant grant-{username} -n {username}-devspaces -o jsonpath='{.status.ca}' | sed 's/^/    /')

cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: AccessToken
metadata:
  name: token-{username}
  namespace: shared-database
spec:
  url: "${URL}"
  code: "${CODE}"
  ca: |
${CA}
EOF
****

しばらくすると、`shared-database` に *Link* リソースが自動的に作成されます。確認しましょう。

{blank}

[.copypaste]
****
oc get link token-{username} -n shared-database
****

リンクのステータスに `Ready` と表示されるまで待ちます。

=== データベースサービスを公開する

ネットワークが構築され、自分の namespace とデータベース namespace が暗号化リンクで接続されました。ただし、ネットワークがあるだけではデータベースにアクセスできません。Service Interconnect に *どのサービス* を自分の namespace に公開するか指定する必要があります。

ここで Listener と Connector を使用します。データベース側の Connector はすでに設定済みです（ステップ 0 で確認しました）。次に、自分の側で対応する Listener を作成します。

{empty} +

==== ステップ 4: データベースをローカルに公開する Listener を作成する

Listener は、自分の namespace にローカルサービスを作成し、暗号化リンクを通じてリモート PostgreSQL データベースにトラフィックを転送します。

{blank}

[.copypaste]
****
cat <<EOF | oc apply -f -
apiVersion: skupper.io/v2alpha1
kind: Listener
metadata:
  name: postgres-listener
  namespace: {username}-devspaces
spec:
  routingKey: postgres
  host: postgres
  port: 5432
EOF
****

IMPORTANT: `routingKey` は `shared-database` namespace の Connector に設定された値と一致させる必要があります。プラットフォームチームは `postgres` に設定しています。

Listener の準備が完了していることを確認します。

{blank}

[.copypaste]
****
oc get listener postgres-listener -n {username}-devspaces
****

次のような出力が表示されます。

確立したリンクは有効なまま維持されます。次の演習ではこのリンクを使用して、ポリシー申請の取り込み、データベースへの保存、PDF ポリシー文書のレンダリングという一連のデータフローを実装します。

=== この演習の先へ: 大規模環境での Service Interconnect

このラボでは、概念を説明するためのシンプルな構成として、同じクラスター上の2つの namespace を接続しました。実環境では、複数のクラスター、リージョン、クラウドプロバイダーにまたがるサービスを接続し、すべてが同じセキュアメッシュを共有するときに Service Interconnect の真価が発揮されます。

各地域に店舗を展開し、それぞれで AI を活用したサービスを実行する小売企業を考えてみましょう。エッジサイトはトレーニングデータを収集し、ローカルにデプロイされたモデルで推論を実行します。冗長化されたオンプレミスのデータセンターが、新しい AI/ML モデルのトレーニングや更新版の店舗への配信など、負荷の高い処理を担います。地域ハブは、近隣のエッジからのトラフィックを集約してからコアに転送します。

{blank}

各エッジサイトはトレーニングデータをコアに送信し、更新されたモデルを取得します。サイト間に複数のリンクを設けることで冗長なルーティングを実現し、ある経路に障害が発生しても別の経路でトラフィックを流せます。ハブはさらにレジリエンスを高めます。フランクフルトのハブが停止した場合、エッジはシンガポール経由にルートを切り替えられます。冗長化されたデータセンターにより、メンテナンス中や障害発生中も AI パイプラインを利用できます。

ここでも、学習した2段階のパターンが適用されます。Site とリンクでネットワークを形成し、Listener と Connector で各拠点の特定のサービスを公開します。異なるのは規模です。1つのクラスター上の2つの namespace ではなく、複数のリージョン、ハブ、データセンターにまたがります。しかし、基本となる構成要素は同じです。
