== トークンレート制限

認証が整ったら、次の制御層はトークン消費です。 **TokenRateLimitPolicy** は、従来のレート制限のように単純にリクエスト数を数えるのではなく、LLM 応答で実際に *使用されたトークン* を追跡します。

レート制限ポリシーは、AI の機能とコストおよびリソース制御を組み合わせる強力な方法です。この演習では、Customer Profile Tool がトークン予算を使って、どの階層の分析を出力するかを決定する仕組みを確認します。

すべての LLM リクエストは計算能力を消費し、より豊富な分析ほど多くの計算資源を必要とします。AI の採用が進むにつれて、コストとインフラ容量の管理は重要になります。レート制限ポリシーは、各サービス全体でのトークン使用量を制御するのに役立ちます。

この演習では、Customer Profile Tool は単純なレート制限にとどまらず、段階的に分析レベルを下げる戦略を採用します。まず *Gold* 分析を試み、Gold 予算が使い切られたら *Silver* にフォールバックして、より低コストで有用なプロファイルを生成し続けます。両方の予算が尽きた場合にのみ、リクエストは拒否されます。

=== TokenRateLimitPolicy を適用して確認する

TokenRateLimitPolicy はゲートウェイレベルのリソースです。階層ごとのトークン予算を定義し、実行中のアプリケーションとは独立してゲートウェイに適用させます。

. _DevSpaces_ で kbd:[+] アイコンをクリックして新しいターミナルタブを開きます（後でテストできるよう、_Camel_ が実行中の前のタブはそのまま残してください）。
+
[#terminal-tab]
image::module-03/m5/devspace_terminal_new_tab.png[Dev Spaces のターミナル,width=70%]
+
[.overlay]
****
[.target]
terminal-tab

[.arrows]
{x: 38, y: 67, rot: -45, size: 3}
****
+
{empty} +
+
NOTE: このポリシーはインフラストラクチャ層で動作するため、エージェントを実行したままでも適用でき、再起動は不要です。
+
{empty} +

. 各階層のトークン予算を確認し、ポリシーを名前空間に適用します。
+
--
このポリシーは、各階層のコストを反映した 2 つのトークン予算を定義します。

* *Gold* — より豊富な分析、より高い計算コスト。更新ウィンドウが長く、より厳しいトークン許容量です。
* *Silver* — より軽い分析、より低い計算コスト。更新がより速く、より寛大なトークン許容量です。
--
+
{blank}
+
以下の TokenRateLimitPolicy を確認し、次の yaml を新しいターミナルタブに *貼り付けて適用* してください。
+
{blank}
+
[.copypaste]
****
oc apply -f - <<EOF
apiVersion: kuadrant.io/v1alpha1
kind: TokenRateLimitPolicy
metadata:
  name: openai-token-limits
  namespace: {user-username}-devspaces
spec:
  targetRef:
    group: gateway.networking.k8s.io
    kind: HTTPRoute
    name: ai-proxy-route
  limits:
    gold:
      rates:
        - limit: 50
          window: 4m
      when:
        - predicate: |
            auth.identity.groups.split(",").exists(g, g == "gold")
      counters:
        - expression: auth.identity.userid
    silver:
      rates:
        - limit: 500
          window: 2m
      when:
        - predicate: |
            auth.identity.groups.split(",").exists(g, g == "silver")
      counters:
        - expression: auth.identity.userid
EOF
****
+
YAML が上で説明した階層別の予算に対応していることに注目してください。`gold` はより厳しい制限と長いウィンドウを持ち、`silver` はより寛大な許容量で、より速く更新されます。
+
[IMPORTANT]
====
TokenRateLimitPolicy は AuthPolicy に依存します。ここで参照している `auth.identity.groups` と `auth.identity.userid` フィールドは、AuthPolicy の `response.success.filters` セクションによって設定されます。AuthPolicy がなければ、TokenRateLimitPolicy には評価するための ID コンテキストがありません。
====
+
{empty} +

[.verification]
****
Gold の予算がなくなったあとに Silver が表示され、最後に両方の予算が尽きたときに 429 エラーが出る、という流れを確認できましたか？

[.success]
階層化されたトークンレート制限と、分析レベルを段階的に下げる戦略を正常に適用できました。

[.fail]
AuthPolicy と TokenRateLimitPolicy の両方が Enforced 状態であることを確認してください。トークン予算が更新されるまで待ってから、もう一度試してください。
****
