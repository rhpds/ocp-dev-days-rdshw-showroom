== はじめに

Apache Kafka を介して Matrix と Rocket.Chat をつなぐ統合フローを構築します。これにより、分離されたイベント駆動型アーキテクチャを実現し、新しいシステムを迎え入れる準備が整います。

{empty} +


=== 簡単なおさらい

お客様は *Matrix* で Policy Applications について問い合わせ、サポート担当者は *Rocket.Chat* から応答します。目標は、両方のプラットフォームを橋渡しし、メッセージがシームレスに行き来するようにすることです。

{empty} +

=== なぜ中央に Kafka を置くのか?

Matrix と Rocket.Chat を直接つなぐのではなく、ストリーミングの基盤としてその間に *Kafka* を配置します。これにより、2 つのプラットフォームは分離され、どちらも相手を知る必要がありません。各システムは Kafka を通じてメッセージを単純に公開し、消費するだけです。

なぜこれが重要なのでしょうか? それは、アーキテクチャの拡張性が高まるからです。ヘルプデスクツール、通知サービス、AI エージェントなど、どんな新しいシステムでも、既存のフローに手を加えることなく、同じ Kafka トピックに接続できます。

=== 共通データモデル

これをきれいに機能させるために、Kafka 上の共通言語として *標準データモデル* を採用します。プラットフォーム固有の形式どうしを直接変換するのではなく (Matrix から Rocket.Chat へ)、各フローは 2 段階で変換します。

* *Inbound*: プラットフォーム固有の形式 → 標準データモデル (Kafka へ)
* *Outbound*: 標準データモデル → プラットフォーム固有の形式 (Kafka から)

これにより、各システムは他のすべてのシステムと個別に連携するのではなく、*1 つ* の共通インターフェースとだけ統合すればよくなります。

=== 4 つのフロー、1 つのパターン

Kafka を介して Matrix と Rocket.Chat を双方向につなぐには、4 つの個別フローが必要です。

* Matrix → Kafka
* Kafka → Rocket.Chat
* Rocket.Chat → Kafka
* Kafka → Matrix

TIP: 直接接続より手間が増えたように見えるかもしれませんが、4 つすべてでパターンは同じです。このラボでは、そのうちの *1 つ* を作成することに集中します。残りも同じ手順で進められ、最後に有効化されます。
