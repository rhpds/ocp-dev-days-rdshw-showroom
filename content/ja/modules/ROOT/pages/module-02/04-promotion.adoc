= 次の段階へ進む
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

サンドボックスのイメージはクリーンです -- 脆弱性は対処済み、ベースイメージは強化済み、コミットは署名済みです。ここで、保護されたパイプライン段階へ変更を進めるときです。マージリクエストのチェック、マージ後のビルド、本番へのタグベースのプロモーションです。

サンドボックスとは異なり、これらのパイプラインはセキュリティポリシーを **強制** します。署名されていないコミット、ポリシー違反、承認の不足はプロモーションをブロックします。

+
image::m02-gitlab-mr-pipeline-running.png[マージがブロックされた状態で実行中の MR チェックパイプライン,link=self,window=blank,width=700]

+
image::m02-rhdh-mr-check-pipeline.png[Developer Hub で Parasol Insurance Secured 上に表示された MR チェックパイプライン,link=self,window=blank,width=700]

* **コミット署名を検証** -- `ENFORCE=true` により、署名されていないコミットは **パイプラインに失敗** します
* MR ブランチからイメージを **ビルド** します
* ACS ポリシーに照らしてイメージを **スキャンし、チェック** します

. GitLab のマージリクエストページに戻ります
* 「Merge」ボタンが有効になっているので、マージできます。ただし、その前に
* Activity の最新エントリーまでスクロールすると、署名ステータス、ACS ポリシー結果、脆弱性数を含む **🔀 Merge Request Check Results** コメントが投稿されています
* pre-check が成功した場合、失敗内容と修正方法を確認するほどは興味深くありません。あなたにとっては情報提供用です（成功しているため）
+
image::m02-gitlab-mr-ready-to-merge.png[パイプラインが通過し、マージ準備完了のマージリクエスト,link=self,window=blank,width=700]
+
image::m02-gitlab-mr-results.png[署名と ACS 検証を示すマージリクエストチェック結果,link=self,window=blank,width=700]

=== 演習 3: リクエストをマージする

. すべてのチェックに合格すると、**Merge** ボタンが使用可能になります。
+
NOTE: パイプラインが失敗した場合（たとえば署名のないコミット）、マージはブロックされます。GitLab はこれを強制するために `onlyMergeWhenPipelineSucceeds` で設定されています。

. **Merge** をクリックします。
+
これにより **post-merge build pipeline** が起動します -- **__final image__** は `main` からビルドされ、Tekton Chains によって署名と証明が行われ、Quay に保存されて preprod 環境へデプロイされます。

== セクション 2: 本番環境へプロモートする

マージ後のビルドで、`main` ブランチから署名済みイメージが作成されました。これを本番環境へプロモートするには、**Git tag** を作成します -- これが tag-promote パイプラインを起動します。

=== 演習 1: タグを作成する

. GitLab で **Repository** → **Tags** に移動します。

. **New tag** をクリックします。

. タグ名を入力し（例: `v2.0`）、ソースとして `main` ブランチを選択します。
+
image::m02-gitlab-create-tag.png[GitLab でタグを作成している様子,link=self,window=blank,width=700]

. **Create tag** をクリックします。

* **SBOM** を生成して TPA にアップロードする
* イメージをタグ付きバージョンとしてレジストリーにコピーする
* 本番デプロイメントを更新するために GitOps manifests リポジトリーで **merge request** を開く

. Developer Hub で **Parasol Insurance (Secured)** コンポーネントに移動し、**CI** タブをクリックします。
+
`parasol-insurance-secured-tag-promote` のパイプライン実行を探します。

+

=== 演習 3: Conforma のポリシー違反を理解する

. **Conforma (ec)** の検証は、イメージの署名済み証跡を一連のポリシーに照らしてチェックします。次の内容が表示されるはずです:
* ✅ **Image signature check** -- イメージは Tekton Chains によって署名されています
* ✅ **Attestation signature check** -- 証跡は署名済みで有効です
* ✅ **Commit must be signed** -- SLSA 証跡が、コミットが署名されていたことを証明します
* ✅ **ACS checks passed** -- イメージスキャンとポリシーチェックの結果が証跡に含まれています
* ✅ **SonarQube quality gate** -- コード品質メトリクスが証跡に含まれています
* ❌ **Parasol Release Approved** -- リリース承認の証跡が見つかりません
+


. イメージがリリース承認されていないため、パイプラインは正しくプロモーションをブロックします。イメージには **signed attestation of a release approval** が付与されていません

=== なぜこれが重要なのか?

本番にデプロイされるイメージには、完全な **SLSA provenance chain** が付与されます:

* **Signed commit** -- 検証済みの開発者 ID に追跡可能
* **SLSA attestation** -- ビルドパイプラインが実行されたこと、どのタスクが実行されたか、そして何を生成したかを証明する
* **ACS scan results** -- 証跡に組み込まれた脆弱性評価
* **SonarQube results** -- 証跡内のコード品質メトリクス
* **Signed approval** -- リリースに対する明示的な人の承認
* **SBOM** -- イメージ内コンポーネントの完全な一覧で、継続的な脆弱性照合のために TPA に保存される

これは単なるチェックボックスの演習ではありません -- すべての証拠が暗号学的に署名され、個別に検証可能です。

=== どのように実現したのか?

演習を読みやすく保つために、詳細を以下に追加しました。展開して、どのように実現したかを読んでください。

.**Open to view implementation details**
[%collapsible]
====
**Tekton Chains** は Sigstore の keyless signing を使用して、パイプラインアーティファクトに自動で署名します:

* 各パイプライン実行後、Chains はパイプラインの service account の ID を使って Fulcio から短命の証明書を要求します
* すべてのタスク結果を含む **SLSA provenance attestation** を作成します
* 証跡と署名は **Rekor**（transparency log）に記録され、レジストリー内のイメージに添付されます

**Conforma (Enterprise Contract)** は、GitLab の {gitlab_url}/parasol/conforma-policies[`conforma-policies` repository on GitLab^] に保存された一連の Rego ポリシーに対して証跡を検証します。`parasol-software-supply-chain` バンドルのポリシーは次をチェックします:

* 必要なタスクが実行されたこと（verify-commit-signature, acs-image-scan, acs-image-check, sonar-scan）
* コミット署名ステータスが `SIGNED` であること（unsigned や bot commit ではないこと）
* ACS ポリシーチェックが通過したこと
* SonarQube quality gate が通過したこと
* 署名済みのリリース承認証跡がイメージに存在すること

image::m02-gitlab-conforma-policies.png[GitLab の Conforma ポリシーリポジトリー,link=self,window=blank,width=700]

**approval attestation** は、predicate type `https://parasol-insurance.com/releases/v1` を持つカスタム in-toto attestation です。これは承認者の ID によって（Fulcio 経由で）署名され、Chains attestation とともにイメージに添付されます。

現在本番にあるイメージに関連付けられた署名済み証跡を確認したい場合は、Developer Hub の **Parasol Insurance (Secured)** コンポーネント経由で **Release Approval** アプリに戻ってください:

image::m02-rhdh-release-approval-link.png[Parasol Insurance Secured コンポーネント上の Release Approval リンク,link=self,window=blank,width=400]

タグをクリックすると、そのイメージに関連付けられた署名済み証跡を確認できます:

image::m02-approval-inspect-attestations.png[タグをクリックして Inspect Attestations を表示,link=self,window=blank,width=500]

ここでは、カスタム attestation の署名者 ID と、Tekton Chains によって署名された自動生成 attestation の両方を確認できます:

image::m02-approval-attestation-details.png[Release Approval と SLSA Provenance および署名者 ID を表示する attestation 詳細,link=self,window=blank,width=700]

**Attestation Detail** セクションでは、イメージとともに保存された attestation を確認できます:

image::m02-approval-attestation-json.png[in-toto statement と predicate および subject を表示する Attestation Detail,link=self,window=blank,width=700]

**SBOM** は **syft** を使って生成され、開発者とバージョンタグを識別するラベル付きで TPA にアップロードされます。TPA は取り込まれた脆弱性データと SBOM を継続的に照合し、デプロイ済みイメージのセキュリティ状態を継続的に可視化します。
====

=== 確認

ここまでで、次のことを行ったはずです:

* 署名済み MR をマージし、マージ後ビルドの成功を確認した
* タグを作成し、承認不足により tag-promote パイプラインが失敗するのを確認した
* リリースを承認し、Conforma 検証が通過するのを確認した
* 完全な SLSA provenance chain を使って本番デプロイメントを検証した
