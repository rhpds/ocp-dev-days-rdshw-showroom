= 次の段階へ進む
include::partial$_attributes.adoc[]
:imagesdir: ../../assets/images

サンドボックスのイメージはクリーンです -- 脆弱性への対処、ベースイメージの強化、コミットへの署名が完了しています。ここからは、保護されたパイプラインの各段階、つまりマージリクエストのチェック、マージ後のビルド、タグベースでの本番環境へのプロモーションへ変更を進めます。

サンドボックスとは異なり、これらのパイプラインではセキュリティポリシーが **強制** されます。未署名のコミット、ポリシー違反、承認の不足があると、プロモーションはブロックされます。

=== 演習 1: マージリクエストを作成する

. GitLab を開き、`parasol-insurance-secured` リポジトリー内のサンドボックスブランチに移動します。
+
Developer Hub のサンドボックスコンポーネントで **View Source** をクリックすると、すばやく見つけられます。

image::m02-rhdh-sandbox-view-source.png[サンドボックスコンポーネントページの View Source,link=self,window=blank,width=700]

. **Create merge request** をクリックします（または **Merge Requests** → **New merge request** に移動します）。
+
image::m02-gitlab-create-mr.png[GitLab の Create merge request ボタン,link=self,window=blank,width=700]

. ソースブランチにサンドボックスブランチを、ターゲットブランチに `main` を設定します。
+
image::m02-gitlab-new-mr-form.png[ソースブランチとターゲットブランチを表示する新しいマージリクエストのフォーム,link=self,window=blank,width=700]

Sec-fix done, security posture improved

+
「Description」を削除し、 **Create merge request** をクリックします。

=== 演習 2: MR チェックパイプラインを確認する

. マージリクエストを作成すると、チェックパイプラインが自動的に起動します。「このビルドは preprod でビルドできるか、チェックに合格するか、標準に準拠しているか」を確認します。これに失敗すると、変更を含むブランチはマージできません。これが **merge request check pipeline** です -- サンドボックスではなく、Parasol の保護されたビルド名前空間で実行されます。
+
image::m02-gitlab-mr-pipeline-running.png[マージがブロックされた状態で実行中の MR チェックパイプライン,link=self,window=blank,width=700]

. GitLab でパイプラインビューを開き、いずれかのタスクをクリックします。Developer Hub で MR Check Pipeline Run が開きます。
+
image::m02-gitlab-mr-pipeline-jobs.png[コミット検証と ACS ジョブを表示する GitLab の MR パイプライン,link=self,window=blank,width=700]

. コンポーネントに注目してください。もうサンドボックスではなく、 `Parasol Insurance (Secured)` です。
+
image::m02-rhdh-mr-check-pipeline.png[Developer Hub の Parasol Insurance Secured で実行中の MR チェックパイプライン,link=self,window=blank,width=700]

. MR チェックパイプラインでは、次の処理が行われます:
* **コミット署名を検証** -- `ENFORCE=true` の場合、未署名のコミットがあると **パイプラインは失敗** します
* MR ブランチからイメージを **ビルド** します
* ACS ポリシーに照らしてイメージを **スキャンしてチェック** します
* GitLab にコミットステータスと詳細な MR コメントとして **結果を報告** します

. パイプラインが完了するまで待ちます。

. GitLab のマージリクエストページに戻ります。
* 「Merge」ボタンが有効になっているためマージできますが、その前に次の点を確認します。
* Activity の最新エントリーまでスクロールすると、署名ステータス、ACS ポリシーの結果、脆弱性の数を含む **🔀 Merge Request Check Results** コメントが投稿されています。
* 事前チェックに成功しているため、問題点や修正方法を確認するときほど興味深いものではありませんが、今回は参考情報として確認できます。
+
image::m02-gitlab-mr-ready-to-merge.png[パイプラインに合格し、マージの準備ができたマージリクエスト,link=self,window=blank,width=700]
+
image::m02-gitlab-mr-results.png[署名と ACS の検証結果を示すマージリクエストのチェック結果,link=self,window=blank,width=700]

=== 演習 3: マージリクエストをマージする

. すべてのチェックに合格すると、 **Merge** ボタンが使用可能になります。
+
NOTE: パイプラインが失敗した場合（たとえば、コミットが未署名の場合）、マージはブロックされます。GitLab はこれを強制するため、 `onlyMergeWhenPipelineSucceeds` が設定されています。

. **Merge** をクリックします。
+
これにより **post-merge build pipeline** が起動します。 `main` から **__final image__** がビルドされ、Tekton Chains によって署名と証明が行われ、Quay に保存されて preprod 環境にデプロイされます。
+
image::m02-rhdh-post-merge-pipeline.png[Developer Hub のマージ後ビルドパイプライン,link=self,window=blank,width=700]

== セクション 2: 本番環境へプロモートする

マージ後のビルドで、 `main` ブランチから署名済みイメージが作成されました。これを本番環境へプロモートするには、 **Git tag** を作成します。これによって tag-promote パイプラインが起動します。

=== 演習 1: タグを作成する

. GitLab で **Repository** → **Tags** に移動します。

. **New tag** をクリックします。

. タグ名（例: `v2.0`）を入力し、ソースとして `main` ブランチを選択します。
+
image::m02-gitlab-create-tag.png[GitLab でのタグ作成,link=self,window=blank,width=700]

* レジストリーからイメージの SHA を取得する

* **SBOM** を生成して TPA にアップロードする

* 本番デプロイメントを更新するため、GitOps マニフェストのリポジトリーで **merge request** を作成する

. Developer Hub で **Parasol Insurance (Secured)** コンポーネントに移動し、 **CI** タブをクリックします。

`parasol-insurance-secured-tag-promote` パイプラインの実行を探します。

=== 演習 3: Conforma のポリシー違反を理解する

. **Conforma (ec)** の検証では、イメージの署名済みアテステーションを一連のポリシーに照らしてチェックします。次の結果が表示されます:
* ✅ **Image signature check** -- イメージは Tekton Chains によって署名されています
* ✅ **Attestation signature check** -- アテステーションには署名があり、有効です
* ✅ **Commit must be signed** -- SLSA 証明書により、コミットが署名済みであることが証明されています
* ✅ **ACS checks passed** -- イメージスキャンとポリシーチェックの結果がアテステーションに含まれています
* ✅ **SonarQube quality gate** -- コード品質のメトリクスがアテステーションに含まれています
* ❌ **Parasol Release Approved** -- リリース承認のアテステーションが見つかりません
+


. イメージがリリース承認されていないため、パイプラインは正しくプロモーションをブロックします。イメージにはリリース承認を示す **署名済みアテステーション** が添付されていません。

=== なぜこれが重要なのか?

本番環境にデプロイされたイメージには、完全な **SLSA provenance chain** が備わっています:

* **Signed commit** -- 検証済みの開発者 ID まで追跡可能
* **SLSA attestation** -- ビルドパイプラインの実行、実行されたタスク、その結果を証明
* **ACS scan results** -- アテステーションに組み込まれた脆弱性評価
* **SonarQube results** -- アテステーションに含まれるコード品質のメトリクス
* **Signed approval** -- リリースに対する明示的な人の承認
* **SBOM** -- イメージ内コンポーネントの完全な一覧。継続的な脆弱性照合のために TPA に保存されます

これは単なるチェックボックスを埋める演習ではありません。すべての証拠に暗号学的な署名が付与され、個別に検証できます。

=== どのように実現したのか?

演習を読みやすくするため、詳細を以下に追加しました。展開して実装方法を確認してください。

.**実装の詳細を表示**
[%collapsible]
====
**Tekton Chains** は Sigstore のキーレス署名を使って、パイプラインの成果物に自動的に署名します:

* パイプラインの実行ごとに、Chains はパイプラインのサービスアカウントの ID を使って Fulcio に短期間有効な証明書を要求します
* すべてのタスクの結果を含む **SLSA provenance attestation** を作成します
* アテステーションと署名は **Rekor**（透明性ログ）に記録され、レジストリー内のイメージに添付されます

**Conforma (Enterprise Contract)** は、GitLab 上の {gitlab_url}/parasol/conforma-policies[`conforma-policies` リポジトリー^] に保存された一連の Rego ポリシーに照らしてアテステーションを検証します。`parasol-software-supply-chain` バンドル内のポリシーでは、次の項目をチェックします:

* 必須タスクが実行されていること（verify-commit-signature, acs-image-scan, acs-image-check, sonar-scan）
* コミット署名のステータスが `SIGNED` であること（未署名や bot のコミットではないこと）
* ACS ポリシーチェックに合格していること
* SonarQube quality gate に合格していること
* 署名済みのリリース承認アテステーションがイメージに存在すること

image::m02-gitlab-conforma-policies.png[GitLab 上の Conforma ポリシーリポジトリー,link=self,window=blank,width=700]

**承認アテステーション** は、predicate type `https://parasol-insurance.com/releases/v1` を持つカスタム in-toto アテステーションです。承認者の ID によって（Fulcio 経由で）署名され、Chains のアテステーションとともにイメージに添付されます。

現在本番環境にあるイメージに関連付けられた署名済みアテステーションを確認するには、Developer Hub の **Parasol Insurance (Secured)** コンポーネントから **Release Approval** アプリに戻ります:

image::m02-rhdh-release-approval-link.png[Parasol Insurance Secured コンポーネントの Release Approval リンク,link=self,window=blank,width=400]

タグをクリックすると、そのイメージに関連付けられた署名済みアテステーションを確認できます:

image::m02-approval-inspect-attestations.png[タグをクリックして Inspect Attestations を表示,link=self,window=blank,width=500]

ここでは、カスタムアテステーションの署名者 ID と、Tekton Chains によって署名された自動生成のアテステーションの両方を確認できます:

image::m02-approval-attestation-details.png[Release Approval と SLSA Provenance、および署名者 ID を示すアテステーションの詳細,link=self,window=blank,width=700]

**Attestation Detail** セクションでは、イメージとともに保存されているアテステーションを確認できます:

image::m02-approval-attestation-json.png[predicate と subject を含む in-toto ステートメントを表示する Attestation Detail,link=self,window=blank,width=700]

**SBOM** は **syft** を使って生成され、開発者とバージョンタグを識別するラベルとともに TPA にアップロードされます。TPA は取り込まれた脆弱性データと SBOM を継続的に照合し、デプロイ済みイメージのセキュリティ状態を継続的に可視化します。
====

=== 確認

ここまでで、次のことを行ったはずです:

* 署名済み MR をマージし、マージ後ビルドの成功を確認した
* タグを作成し、承認の不足によって tag-promote パイプラインが失敗することを確認した
* リリースを承認し、Conforma の検証に合格したことを確認した
* 完全な SLSA provenance chain を使って本番デプロイメントを検証した

'''
