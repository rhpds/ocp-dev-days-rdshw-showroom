== Lab 5 - Governance degli LLM

Posiziona un livello di governance davanti all'endpoint LLM usando Connectivity Link. Applica l'autenticazione con chiave API e limiti di frequenza basati sui token per più livelli di servizio.

{empty} +

=== Lo scenario

Nei lab precedenti hai creato un agente AI che risolve i problemi dell'assistenza clienti tramite il linguaggio naturale. L'agente interroga il database, aggiorna i record e rigenera i documenti delle polizze, tutto dall'interfaccia di chat.

Ora vuoi estenderlo con una nuova funzionalità: **analisi del profilo cliente**. Quando un agente di supporto chiede informazioni su un cliente, l'AI ne analizza i dati e restituisce un riepilogo strutturato. Sono disponibili due livelli di analisi:

* **Gold** -- cronologia completa delle polizze, dei sinistri e stato del programma fedeltà.
* **Silver** -- polizze recenti e informazioni di base sul profilo.

Gold consuma più token perché l'analisi è più approfondita e la risposta più ricca. Silver è più leggero. Il sistema è progettato con una strategia di fallback: se il budget di token del livello Gold si esaurisce, il servizio passa a Silver. Se si esaurisce anche quello del livello Silver, la richiesta viene rinviata.

Ma prima che tutto questo possa funzionare, serve la governance. Chi può accedere all'endpoint LLM? Quanti token può consumare ciascun tier? Senza controlli, niente impedisce un consumo incontrollato che esaurisca il budget API dell'organizzazione.

In questo lab aggiungerai un **livello di governance** davanti all'endpoint LLM usando link:https://www.redhat.com/en/technologies/cloud-computing/connectivity-link[*_Red Hat Connectivity Link_*,window=_blank]. Implementerai due policy:

* **AuthPolicy** -- Controlla _chi_ può accedere all'endpoint con l'autenticazione tramite chiave API e l'autorizzazione basata sui gruppi.
* **TokenRateLimitPolicy** -- Controlla _quanto_ può consumare ciascun tier applicando limiti di frequenza basati sull'utilizzo effettivo dei token.

{empty} +

=== Perché Connectivity Link?

È proprio il tipo di problema per cui è stato progettato _Red Hat Connectivity Link_. Basato sul progetto link:https://kuadrant.io/[_Kuadrant_,window=_blank], porta la governance consapevole dell'AI in *Kubernetes*:

* **Limiti di frequenza consapevoli dei token** -- i limiti si basano sui token effettivamente consumati, non sul numero di richieste. Questo rende praticabili i servizi AI a più livelli: ciascun livello riceve un proprio budget di token, applicato al gateway.
* **Nessuna modifica al codice** -- le policy vengono applicate a livello infrastrutturale. Il tuo agente AI e il codice di integrazione restano invariati.
* **Nativo per Kubernetes** -- le policy sono CRD standard, applicate con `oc apply`, archiviate in Git e revisionate nelle PR. Non servono una console di gestione separata né un control plane del vendor.
* **Componibile** -- una policy estrae l'identità, un'altra la usa per assegnare budget di token distinti a ciascun livello. Si sovrappongono in modo dichiarativo.

Queste funzionalità derivano dal modo in cui Connectivity Link si basa sullo standard _Kubernetes Gateway API_. Prima di iniziare a configurare le policy, esaminiamo il modello Gateway API.

{empty} +

=== Il modello Gateway API

Connectivity Link si basa su _Kubernetes Gateway API_, lo standard per gestire l'instradamento del traffico in _Kubernetes_. Comprendere questo modello renderà intuitivi gli esercizi successivi.

Ecco i componenti fondamentali:

* **GatewayClass + Gateway** -- sono gestiti dal platform team. Definiscono _come_ il traffico entra nel cluster. Sono già stati predisposti.
* **HTTPRoute** -- è gestito dal platform team o dal team di sviluppo. Definisce _dove_ viene instradato il traffico (in questo caso, all'API LLM).
